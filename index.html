OPERATION 01 // HYBRID IDENTITY ENTERPRISE ASSESSMENT

Hybrid Identity Attack-Path Assessment

Regional financial-services enterprise with on-premises Active Directory and hybrid Microsoft identity services.

Objective

Assess routes from standard-user access to privileged enterprise assets.

My role

Independent assessment lead

Key result

500+ high-risk identity paths triaged and prioritised by root cause and impact.

View case study +

Objective

Determine whether compromise of a standard user account could be chained into privileged access through identity misconfigurations, delegated permissions, certificate services, or service-account relationships.

Approach

BloodHound and targeted directory enumeration were used to construct the identity graph. High-risk relationships were manually reviewed to separate theoretical paths from realistically exploitable chains.

Defender outcome

The final output translated the attack graph into a remediation programme based on root cause, blast radius and remediation value. Defenders could focus on breaking multiple attack paths with a smaller number of control changes, rather than remediating hundreds of graph edges individually.

500+ high-risk identity paths triaged and prioritised

Attack path assessed

  1. Standard User
  2. Delegated Group Control
  3. Service Account
  4. Certificate / Identity Misconfiguration
  5. Privileged Account
  6. High-Value Enterprise Asset

Attack surface

Active Directory · ADCS · Kerberos · Group Policy · Service Accounts · ACLs · Hybrid Identity

Observation

Multiple identity relationships individually appeared low risk but became significant when chained together. Several paths shared the same underlying root causes:

  • Excessive delegated permissions
  • Long-lived service-account privileges
  • Nested group relationships
  • Weak ownership of privileged objects
  • Certificate-service configuration exposure

Hypothesis

An attacker beginning with ordinary domain-user access could potentially move through existing trust relationships without requiring exploitation of a software vulnerability.

Validation

Where authorised, representative paths were safely validated to establish practical escalation routes. Candidate paths were manually reviewed and prioritised according to:

  • Exploitability
  • Privilege gained
  • Number of prerequisite conditions
  • Blast radius
  • Accessibility from a realistic initial foothold

Evidence

Evidence collected included:

  • Identity relationship graphs
  • Object ACLs
  • Group membership relationships
  • Certificate configuration
  • Service-account privilege relationships
  • Affected asset inventory
  • Reproducible attack-path documentation

Result

500+ high-risk identity paths triaged and prioritised. Findings were consolidated around the underlying control failures responsible for generating the paths, rather than reporting each path as a separate issue.

Detection opportunities

The assessment identified opportunities for defenders to monitor:

  • Unusual privileged-group modifications
  • Certificate enrolment activity
  • Abnormal authentication patterns
  • Service-account use outside expected systems
  • Enumeration of privileged directory objects

From repeated acceptance to duplicate rejection.

Saved assessment and retest records show a business-operation replay finding progressing from observed duplicate acceptance, through an inconclusive retest, to recorded closure after an explicit duplicate-rejection response.

  1. INITIAL ASSESSMENTRepeat accepted

    Identical requests were recorded as accepted more than once.

  2. FIRST RETESTInconclusive

    Behaviour was not deterministically reproduced; the finding remained unclosed.

  3. LATER RETESTDuplicate rejected

Inspect sanitised evidence +

Observation

The original assessment recorded repeated acceptance of an identical confirmation request, including reuse of a business reference with changed client-supplied identifiers.

Potential impact

Duplicate processing, repeated notifications or reconciliation errors, depending on downstream behaviour. Accepted API responses alone do not establish duplicate financial posting or settlement.

Closure evidence

The later retest recorded an explicit duplicate-rejection response for an existing transaction identifier. The saved tracker marked the finding closed and noted that an idempotency control was observed.

Remediation direction

Enforce backend idempotency using stable operation identifiers and business-reference checks, handle repeats consistently and retain duplicate-replay cases in regression testing.

Evidence limits

OPERATION 03 // AI SECURITY R&D CONTROLLED LAB / R&D

Agentic AI Trust-Boundary Assessment

Controlled AI-agent lab containing an LLM, retrieval layer, memory, external tools and human-approval controls.

Objective

Evaluate whether untrusted content can cross an AI agent’s authority boundaries.

My role

Independent assessment lead

Key result

Design recommendations to limit tool authority and reduce potential blast radius in a controlled lab.

View case study +

Objective

Determine whether untrusted instructions or retrieved content could influence an AI agent into crossing intended authority boundaries or misusing connected tools.

Approach

The assessment treated the AI model as one component inside a larger security system. Testing concentrated on trust boundaries across user, model, retrieval, memory, tools and external systems.

Defender outcome

The exercise evaluated the maximum authority an agent could exercise if manipulation succeeded. The resulting design recommendations focused on reducing the blast radius available to a compromised or manipulated agent.

Attack path assessed

  1. Untrusted Content
  2. Indirect Prompt Injection
  3. Agent Instruction Manipulation
  4. Tool Selection
  5. Authority Boundary Failure
  6. Unauthorised Action / Data Exposure

Attack surface

LLM Agent · MCP / Tool Interfaces · RAG · Memory · Prompt Boundaries · Human Approval · External Content

Observation

The higher-impact scenario was whether attacker-controlled content could influence a model with tools, credentials, stored context, access to external data and permission to perform actions.

Hypothesis

If trusted and untrusted instructions were insufficiently separated, attacker-controlled content could influence tool use or cause the agent to operate beyond the user's original intent.

Validation

Tests were executed in a controlled laboratory environment using non-production accounts and synthetic data. The evaluation harness tested:

  • Direct prompt injection
  • Indirect prompt injection
  • Retrieval poisoning
  • Malicious tool output
  • Memory contamination
  • Tool misuse
  • Excessive agent authority
  • Sensitive-data exposure
  • Approval bypass
  • Cross-step instruction persistence

Evidence

For every successful or partially successful test, the harness recorded the following to create an auditable chain of the security-sensitive decision:

  • Attacker-controlled input
  • Retrieved context
  • Model decision
  • Requested tool call
  • Approval state
  • Tool result
  • Resulting security impact

Defensive controls evaluated

Controls included:

  • Least-privilege tool permissions
  • Allow-listed operations
  • Structured tool interfaces
  • Separation of trusted and untrusted content
  • Human approval for sensitive actions
  • Short-lived credentials
  • Tool-output validation
  • Logging and replay
  • Memory isolation

Defender outcome

The exercise shifted the security model from preventing every malicious prompt to limiting the authority available when manipulation succeeds.

If manipulation succeeds, what is the maximum authority the agent can exercise?

Research value

Offensive-security testing beyond traditional infrastructure and applications, applying the same core methodology: model the trust boundary → form a hypothesis → validate the attack → preserve evidence → reduce attacker capability.
